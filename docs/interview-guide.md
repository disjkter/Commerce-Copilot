# 简历与面试表达

## 1. 一分钟项目介绍

Commerce Copilot 是一个面向商品推荐和订单售后的多 Agent 电商助手。我没有把它实现成单次大模型调用，而是使用 LangGraph Supervisor 将用户消息拆成 Product Scout、Order Care 和 Conversation Guide 等独立任务，并发执行后再汇总。商品侧采用关键词召回、离线向量召回和 RRF 融合，同时把品类、预算、库存作为硬约束。为了降低事实幻觉，我设计了 Claim–Evidence Grounding，商品价格、订单状态和政策必须引用数据库 Evidence 才能进入最终回答。系统还包含 DeepSeek 结构化规划、本地降级、PostgreSQL 持久化、Alembic 迁移、用户鉴权、多轮会话、偏好记忆和自动化测试。

## 2. 简历项目描述

### 推荐标题

**Commerce Copilot｜基于 LangGraph 的可观测多 Agent 电商助手**

### 推荐技术栈

`Python` · `FastAPI` · `LangGraph` · `DeepSeek` · `PostgreSQL` · `SQLAlchemy` · `Alembic` · `Pydantic` · `FTS/BM25` · `Vector Retrieval` · `RRF`

### 可直接使用的项目要点

- 设计 Supervisor + 3 个领域 Agent 的协作架构，利用 LangGraph `Send` 完成同轮多意图任务的并发 fan-out 与结果汇合，并通过统一 `Mission/AgentReport` 契约隔离领域状态。
- 实现关键词与离线向量双通道召回，通过 RRF 融合排序；将品类、预算和库存下推为数据库硬约束，避免语义相关性突破业务条件。
- 设计 Claim–Evidence Grounding，逐条校验事实引用、字段和值；DeepSeek 超时、非法 JSON 或校验失败时使用本地确定性逻辑降级。
- 基于 PostgreSQL、SQLAlchemy Repository 和 Alembic 管理用户、商品、订单、会话、Evidence 与偏好数据，实现 Token 鉴权、订单归属和会话隔离。
- 支持多轮商品指代、确定性商品对比、个性化偏好以及可解释候补推荐；使用 94 个自动化测试覆盖规划、检索、Grounding、鉴权和迁移流程。

不要在简历中加入尚未完成的 SSE、BGE、pgvector、Redis、云部署和压测数据。

## 3. 这个项目解决了什么问题

普通聊天机器人容易出现三类问题：

1. 混合意图互相干扰，例如推荐商品和查询物流混在一个 Prompt 中。
2. 模型直接生成价格、库存和订单状态，产生事实幻觉。
3. 出错后只能看到最终答案，无法定位是规划、检索还是生成失败。

本项目分别通过多 Agent 任务隔离、Claim–Evidence Grounding 和 Execution Trace 解决这三个问题。

## 4. 高频面试问题

### 为什么需要多个 Agent？

重点不是 Agent 数量，而是职责和失败域。商品检索与订单服务依赖不同数据源、约束和输出字段；拆开后可以并发执行、独立测试，某一分支失败时也能保留其他有效结果。

### `Annotated[list[AgentReport], operator.add]` 有什么作用？

LangGraph 的并发节点会分别返回 `reports`。Reducer 使用 `operator.add` 把各分支列表合并；普通 `list[AgentReport]` 没有声明合并策略，并发写入可能发生覆盖冲突。

### 为什么使用 RRF？

BM25 分数和向量余弦相似度量纲不同，直接加权需要额外归一化和调参。RRF 只使用各通道名次，简单、稳定，适合小数据基线和后续对比实验。

### 为什么品类必须是硬约束？

如果“耳机”只参与相关性评分，“办公”可能让鼠标排到前面。品类、预算和库存属于用户不可违反的约束，必须同时作用于关键词和向量候选集；场景和功能才适合作为软排序特征。

### Grounding 能完全解决幻觉吗？

不能。它能阻止结构化事实与 Evidence 不一致，但不能自动证明主观措辞、数据源本身或检索遗漏是正确的。因此系统还需要可信数据源、检索评测和 bad case 回归。

### 为什么还保留本地 Planner？

LLM 是不稳定外部依赖。没有 Key、超时或 JSON 校验失败时，本地规则仍能覆盖核心商品、订单和问候意图，使服务具备可预测降级能力，也方便离线测试。

### PostgreSQL 和 Redis 分别适合什么？

PostgreSQL 保存用户、订单、会话等需要事务和持久一致性的主数据。Redis 更适合缓存、短期状态、限流和异步队列，后续会作为性能层加入，而不是替代主数据库。

## 5. 可诚实说明的不足

- 当前商品数据规模小，主要验证工程链路。
- 离线向量器是中文二元组特征哈希，不是真正的语义 Embedding。
- 尚未完成 Redis、SSE、云部署和压力测试。
- Grounding 当前是字段级一致性校验，不等同于完整自然语言事实核验。

主动说明边界比夸大项目更可信，同时可以自然引出 `roadmap.md` 中的下一阶段设计。

## 6. STAR 表达示例

**情境：** 个性化查询“300 元以内办公耳机”错误返回了鼠标，因为场景词在向量通道中的相关性压过了品类。

**任务：** 在不牺牲混合检索召回能力的前提下，保证明确业务约束绝不被突破。

**行动：** 将品类提取为结构化参数，在 Repository 层为 FTS 和向量候选集同时增加 SQL 硬过滤；严格结果为空时，只在确认预算是唯一阻塞条件后提供同品类最近预算候补，并生成可校验 Evidence。

**结果：** 系统不再跨品类凑结果，能准确说明预算差额，并通过自动化测试覆盖严格检索、候补推荐和用户接受预算放宽的多轮流程。
